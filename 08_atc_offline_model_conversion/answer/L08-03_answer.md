## 1　三输入模型的 bin 准备与校验

```python
import numpy as np, os

os.makedirs("l08_workspace/multi_in", exist_ok=True)
np.random.seed(0)

specs = [
    ("00_input_ids",      np.random.randint(0, 1000, (1, 128)).astype(np.int64)),
    ("01_attention_mask", np.ones((1, 128), dtype=np.int64)),
    ("02_token_type_ids", np.zeros((1, 128), dtype=np.int64)),
]

for name, arr in specs:
    path = "l08_workspace/multi_in/%s.bin" % name
    arr.tofile(path)
    expect = arr.size * arr.dtype.itemsize
    actual = os.path.getsize(path)
    print("%-20s %-10s %-8s 期望 %6d 实际 %6d %s" % (
        name, arr.shape, arr.dtype, expect, actual,
        "OK" if expect == actual else "不匹配"))
```

三个文件各 `128 × 8 = 1024` 字节。

**为什么用数字前缀。** msame 按输入顺序匹配文件，顺序由文件名排序决定。如果直接用 `input_ids.bin`、`attention_mask.bin`、`token_type_ids.bin`，排序结果是 `attention_mask` → `input_ids` → `token_type_ids`——按字母序，与模型的输入顺序不一致。msame 不会报错，它只按字节数读，三个输入都是 1024 字节，正好都能读进去，结果全错。

这类错误在链路上没有任何一步能拦住，只能靠命名规范预防。

**dtype 是第二个坑。** `input_ids` 是词表索引，int64；不是 float32。写错时字节数会差一倍（1024 对 512），这时反而会报 size 不匹配——比顺序错好查。

**校验函数应该做两件事**：核对每个文件的字节数等于 `prod(shape) × dtype字节宽`；打印排序后的文件列表，人工确认与模型输入顺序对应。第二件事没法自动化，因为 bin 文件里没有名字信息。

## 2　耗时四指标

用课件 4 节的示例数据（`warmup=5`）作为自查参照，实际提交须用本机数据。

```text
原始数据（15 次，ms）
12.83, 1.42, 1.38, 1.45, 1.39, 1.41, 1.37, 1.44, 1.40, 1.38, 1.43, 1.39, 1.41, 1.38, 1.42
```

| 指标 | 数值 | 算法 |
| --- | --- | --- |
| 首次时延 | 12.83 ms | `lat[0]` |
| 含首次的平均 | 2.17 ms | 15 个值的平均 |
| 去预热的平均 | 1.403 ms | 后 10 个值的平均 |
| 标准差 | 0.022 ms | 后 10 个值 |
| P95 | 1.44 ms | 后 10 个值 |
| 吞吐 | 712.8 次/秒 | `1000 / 1.403` |

**含首次与去预热差 54%。** 首次 12.83 ms 是稳定态 1.403 ms 的 9 倍多，这 11.4 ms 的差额里是模型加载、显存分配和算子初始化，与推理本身无关。

模型越小，这个偏差越夸张：DemoNet 只有几千个参数，加载开销几乎全是固定成本，占比极高。换成 ResNet50，稳定态时延升到几毫秒，首次的相对影响就小得多。所以**不能用一个固定的"丢弃前 N 次"规则套所有模型**，要看数据——从第几次开始时延进入稳定区间，就从那里开始统计。

**标准差 0.022 ms，约为均值的 1.6%**，说明这批数据抖动很小。实时应用里这个指标比吞吐更重要：吞吐 700 次/秒但标准差 5 ms 的服务，用户能感觉到卡顿；吞吐 500 次/秒但标准差 0.1 ms 的服务体验更好。平均值看不出这个差别，必须单独报标准差或 P95/P99。

**P95 1.44 ms 与均值 1.403 ms 很接近**，同样印证分布集中。如果 P95 明显高于均值（比如两倍），说明有长尾，要去查是不是有周期性的资源竞争。

## 3　三条报错的定位

**`E19999: Inner Error, Not supported operator: GridSample`**

阶段：ATC 转换。这不是 msame 的错，说明 OM 根本没转出来。

原因：CANN 当前版本不支持 GridSample 算子。它常见于可变形卷积、光流和 STN 类结构。

下一步：先确认 ONNX 里这个算子的 opset 版本，试着提高 `opset_version` 重新导出——有些算子在高版本 opset 里有标准实现，CANN 的支持情况也不同。不行就用基础算子改写等价语义（GridSample 可以用 `grid` 索引加双线性插值手工实现）。都不行才考虑用 Ascend C 写自定义算子，这是实验 4、5 的内容。

**`Expected size: 12288, but given input size: 6144`**

阶段：数据。OM 已经转好了，是喂进去的 bin 不对。

12288 是 `1×3×32×32×4`，也就是 float32 的 DemoNet 输入。给了 6144，正好是一半。两种可能：dtype 写成了 float16（`astype(np.float16)` 或 `dtype=np.float16`）；或者某一维少了一半，比如 shape 写成 `(1, 3, 32, 16)`。

下一步：先算 `prod(shape) × dtype字节宽`，与文件实际大小比对，用课件 6 节的自查代码。数值是整数倍关系时基本都是 dtype 问题，因为 float16 对 float32 正好 2 倍、int8 对 float32 正好 4 倍。

**`terminate called after throwing an instance of 'std::runtime_error'`（msame 启动瞬间）**

阶段：环境。在启动瞬间抛、且是 C++ 层的未捕获异常，说明还没进到模型加载逻辑。

原因：没 source `set_env.sh`，动态库找不到；或者 msame 编译时链接的 CANN 版本与运行时的不一致。

下一步：`echo $ASCEND_TOOLKIT_HOME` 确认环境变量；`ldd $(which msame)` 看有没有 `not found` 的依赖。注意每个 notebook cell 是独立子进程，上一个 cell 的 `source` 不会带过来——这是 notebook 环境里最容易犯的。

**三条题目的共同点**：报错文本本身都没直接指出真正的原因。GridSample 那条说的是 "Inner Error"，size 那条只给数字不说 dtype，runtime_error 那条什么信息都没有。所以要按阶段索引——先判断错在链路的哪一段，再在那一段里查。

## 4　双输出模型的 `--outputSize`

输出 A：`(1, 1000)` float32；输出 B：`(1, 256, 14, 14)` float32。

```text
A: 1 × 1000 = 1000 元素 × 4 字节 = 4000 字节
B: 1 × 256 × 14 × 14 = 50176 元素 × 4 字节 = 200704 字节
```

留 20% 余量：

```bash
--outputSize "4800,240844"
```

（`4000 × 1.2 = 4800`，`200704 × 1.2 = 240844.8`，取整 240844）

**三个要点。**

顺序必须与模型的输出顺序一致，不是按大小排。用 `onnx.load` 读 `graph.output` 确认顺序，或从 `atc` 的转换日志里看。

余量是给动态 shape 留的。这个参数是缓冲区上限，动态场景下实际输出可能小于上限但不能超过。如果 shape 完全静态，按精确值给也可以；有动态维时要按**该维的最大取值**算，再留余量。

不要拍一个"足够大"的数。给 10000000 也能跑，但缓冲区按上限分配，浪费的是设备内存；多输出、大 batch 时这个浪费会变得可观。算出来只多一行代码。

## 5　输入 bin 少 4 字节 **[需实测]**

制造错误：

```python
import numpy as np
x = np.random.randn(1, 3, 32, 32).astype(np.float32)
x.ravel()[:-1].tofile("l08_workspace/input_short.bin")   # 少一个 float32
```

`12288 - 4 = 12284` 字节。跑 msame 后记录完整报错。

**预期**：报 size 不匹配一类的错误，期望值 12288，实际 12284。msame 在加载输入前会核对字节数，所以这个错在推理开始前就抛出，不会得到错误结果。

**为什么这个错反而是好事。** 对比第 1 题的文件顺序错——那种错 msame 检测不到，因为三个文件字节数都对，只是对应关系错了，结果全错但不报错。字节数错至少会被拦住。

**推论**：msame 的输入校验只能查字节数总量，查不了语义。所以字节数对不上时反而好办；字节数刚好对上但含义错了（顺序错、dtype 同宽度但类型不同、shape 各维乘积相同但排布不同，比如 `(1,3,32,32)` 和 `(1,32,32,3)`），才是真正麻烦的情况。这也解释了为什么 `--input_format` 写错属于"不报错但结果错"。

## 7　随机输入为什么可能掩盖问题

**四种典型情况。**

数据相关的控制流永远走不到另一支。模型里有依赖输入数值的 `if`，随机数据恰好总走同一支（见 L08-01 练习 5）。转换把另一支丢了，用随机数据验证发现不了。

FP16 的溢出与下溢跟数值范围绑定。FP16 的表示范围是 ±65504，最小正规数约 6e-5。随机输入的激活值分布在中间区间时一切正常；真实数据让某层激活值超出范围，才会出现 inf 或 0。这类问题只在特定输入上暴露。

argmax 判据在随机输出上没有意义。随机输入产生的 logits 分布均匀，最大值和次大值差距可能很小，argmax 一致纯属偶然。真实数据上模型有明确倾向，argmax 才是有效判据。

量化校准需要真实分布。用了 INT8 量化的模型，校准的缩放系数是按真实数据的数值分布算的。随机数据的分布与真实数据差别很大，用它验证测的不是部署时的实际精度。

**必须用真实数据的场景**：验证精度（任何精度结论都要基于真实数据）；确认动态范围和溢出行为；模型含数据相关控制流；模型经过量化。

**随机输入能用的场景**：只测耗时和吞吐——计算量由 shape 决定，与数值无关；检查链路是否通（能不能加载、能不能跑完、输出 shape 对不对）；压力测试和显存占用测量。

**实践建议**：链路调通用随机数据（快、不需要准备数据集），精度验证一律换真实数据，两步都做。

## 8　msame 通过但业务指标不达标

msame 保证的是"单样本前向的输出与转换前一致"这一件事。业务指标不达标，多数原因在这件事之外。

**预处理不一致——最常见。** 训练时的 resize 插值方式、归一化的 mean/std、通道顺序（RGB 还是 BGR）、padding 策略，部署侧只要有一项不同，模型输入就不是训练时的分布。msame 用的是你自己准备的 bin，如果准备 bin 的代码复用了训练侧的预处理，这个问题就被绕过去了，测不出来。

**后处理不在模型里。** NMS 的 IoU 阈值、置信度阈值、anchor 解码、softmax 温度——这些通常在模型外面，转换不涉及，但直接决定业务指标。

**FP16 误差在困难样本上放大。** msame 用一个样本对齐通过，说明该样本上误差可接受。困难样本的 logits 差距本来就小，累积误差足以改变 argmax。要发现这个，得跑数据集级评测，看整体指标下降了多少。

**动态 shape 的某些档位没测。** 只测了一个档位，其他档位可能有问题。每个档位是独立编译的，理论上应该逐档验证。

**batch > 1 的行为差异。** 只测了 batch=1。某些算子在 batch 维上的实现路径不同，多 batch 时可能有问题。

**长时间运行的稳定性。** 单次推理正确，不代表连续跑几小时不出问题。内存泄漏、显存碎片、温控降频，都要靠长时间压测发现。

**测试数据不代表线上分布。** 这属于机器学习的常规问题，与转换无关，但常被误判成转换问题。

**排查顺序**：先复核预处理和后处理——这两项占实际问题的绝大多数，且改起来最快；再跑数据集级评测，量化下降幅度；然后逐档位、逐 batch 验证；最后才怀疑算子实现差异。

**一句话**：msame 是转换环节的质检，不是模型质量的质检。转换正确是必要条件，不是充分条件。
